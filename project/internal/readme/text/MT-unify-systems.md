# Теория реализации унифицированных систем и отношений между ними

MT-unify-systems · Δρ.ΒοροΗ. · MorangTong creative studio (MTcs) · Редакция 1.0 · 2026-11-24

## Аннотация

Теория описывает, как вводить новую функциональность в программный механизм, чтобы он оставался единым деревом систем, а не набором параллельных реализаций одной и той же задачи. Предмет — отношения между унифицированными системами: направление зависимостей, способы внесения изменений (голова, унифицирующий рефакторинг, ромб), граница между ядром и интерфейсами среды, независимость данных от алгоритмов. Результат — процедура допуска из шести вопросов и порядок приоритетов, в котором поведение стоит выше теории, а теория уступает там, где следование ей усложняет реализацию.

## 1. Область применения

1.1. Теория применяется к программным механизмам, у которых есть ядро и один или несколько интерфейсов среды (терминал, файловый ввод, сетевой вызов и т. п.).

1.2. Положения обязательны при написании нового кода, при изменении существующего и при аудите. Оформление исходного текста и версионирование репозитория теорией не регулируются: для них существуют отдельные документы.

1.3. Теория не зависит от языка программирования. Она требует только возможности выделять модули и направлять зависимости между ними.

1.4. Теория является инструментом, а не целью. Если следование ей делает реализацию тяжелее, чем отступление, действует раздел 5.

## 2. Термины и определения

| Термин | Определение |
|---|---|
| Механизм | Сам разрабатываемый программный продукт. Теория описывает его построение, а не то, как им пользуются. |
| Интерфейс использования | Возможность, которую механизм отдаёт пользователю (например, команда создания проекта). Это обычная система механизма, а не его инициация. |
| Поведение | Совокупность ожиданий пользователя от механизма, выраженная тестами. Инвариантно по отношению к реализации. |
| Реализация | Алгоритмы и их построение, обеспечивающие поведение. Может меняться при неизменном поведении. |
| Система | Единица ядра, решающая одну задачу (учёт истории, доступ к внешнему ресурсу, проверка путей). |
| Ядро | Дерево систем. Каждая система существует в единственном экземпляре. |
| Предшественник | Узел, который данный узел использует внутри себя. |
| Последователь | Узел, который включает данный узел в себя. |
| Интерфейс системы | Слой точек доступа вокруг «сырого» кода системы. Через него система используется остальным миром. |
| Интерфейс среды | Способ взаимодействия с конкретной средой (терминал, каталог файлов-операций). Образует отдельное параллельное дерево. |
| Адаптер среды | Часть параллельного дерева, переводящая спецификацию среды в вызовы точек доступа ядра и результат ядра в представление среды. |
| Спецификация среды | Правила представления и разбора, свойственные конкретной среде: синтаксис команд, формат файла, формат вывода. |
| Управление использованием | Параметры, определяющие, как работает алгоритм (например, включать ли неотслеживаемые файлы в коммит). Принадлежит ядру. |
| Зерно | Единственная точка входа механизма: она собирает конфигурацию, реестры и подключает интерфейсы. |
| Сирота | Функция, нужная только для запуска механизма и нигде больше не встречающаяся. Живёт в самом файле зерна. |
| Голова | Новая функциональность, приходящая поверх системы как дополнение: обвязка или параметризация исполнения. Включает систему в себя и не меняет её. |
| Ромб | Близнец узла: новая версия узла с общими предшественниками, но собственными последователями. Старые последователи остаются у прежнего узла. |
| Унифицирующий рефакторинг | Выделение из узла переиспользуемой части, которая становится предшественником и прежнего узла, и новой механики. |
| Фасад | Слой-посредник между ядром и адаптерами. Допустим только при наличии не менее двух адаптеров. |

## 3. Положения

### 3.1. Поведение и реализация

1. Работа делится на поведение и реализацию. Поведение зафиксировано тестами и меняется только осознанным решением автора.
2. Рефакторинг меняет реализацию и не меняет тесты, контролирующие поведение.

### 3.2. Ядро как дерево систем

1. Каждая система ядра единственна: одна задача — один экземпляр. Параллельные реализации одной задачи (дублирующие конвейеры, разрозненные обёртки над одним ресурсом) не допускаются.
2. Дерево растёт от зерна. Каждая система опирается на уже имеющуюся или расширяет её.
3. Система может быть новой небольшой или собранной после рефакторинга из прежних.

### 3.3. Зерно и сироты

1. Инициация самого механизма принадлежит зерну: оно собирает конфигурацию и реестры, подключает интерфейсы.
2. Функции, нужные только для запуска механизма и нигде больше не встречающиеся, остаются сиротами в файле зерна. Их вынос в другие файлы создаёт видимость принадлежности к чужой системе.
3. Сирота, понадобившийся второй раз, перестаёт быть сиротой и переходит в общую систему.
4. Интерфейс использования (например, создание проекта пользователя) не является инициацией механизма. Это обычная система, и сиротой она не считается.

### 3.4. Интерфейсы среды и параллельные деревья

1. Вокруг «сырого» кода каждой большой системы ядро строит интерфейс: набор точек доступа.
2. Интерфейс среды образует параллельное дерево с той же структурой и теми же правилами, что и ядро. Цепочка зависимостей:

        алгоритм → интерфейс системы ← адаптер спецификации среды ← интерфейс среды

3. Адаптер вызывает ядро, ядро адаптеров не вызывает, не опрашивает и не знает о них.
4. Параллельные деревья не вызывают друг друга и не пользуются правилами друг друга. Общее живёт только в ядре.
5. Фасад вводится только там, где существует не менее двух адаптеров. При одном адаптере ядро отдаёт ему экспортируемые функции напрямую.

### 3.5. Спецификация и управление использованием

1. Перед вводом параметра (например, флага команды) определяется, к чему он относится: к спецификации среды или к управлению использованием.
2. Спецификация среды (синтаксис флага, формат вывода, буфер обмена) остаётся внутри адаптера.
3. Управление использованием (решает, как работает механизм) входит в дерево ядра как параметр системы и определяется один раз. Адаптеры лишь переводят свою запись (флаг, поле файла) в этот параметр.

### 3.6. Данные и алгоритмы

1. Данные и алгоритмы независимы. Данные меняются отдельно: полировка, добавление, расширение. Алгоритм меняется, только когда пересмотрена главная механика и нужен рефакторинг соседних систем.
2. Правка данных, которая тянет за собой правку алгоритма, считается ошибкой построения. Типичный случай — имитация конфигурации «костылями» в коде.
3. Нововведение относится к алгоритмам и допускается, если оно гибко и масштабируемо. Файлы и содержимое, создаваемые под конкретного пользователя, остаются данными и пишутся извне механизма.

### 3.7. Тесты

1. Тест проверяет детерминированность поведения алгоритма: парсеры, классификаторы, правила проверки, цепочки обратимых операций.
2. Данные, способные дрейфовать (тексты справок, шаблоны, значения по умолчанию, подписи вывода), тестами не проверяются: такие тесты ломаются при каждой полировке и не защищают поведение.

### 3.8. Неиспользуемый код

1. Мёртвый код удаляется, а не накапливается в виде закомментированных блоков и резервных копий. Прошлое хранит система контроля версий.

### 3.9. Новая ветвь дерева

1. Новая ветвь, не вписывающаяся в имеющиеся системы, допускается только после обоснования: насколько изменение важно и каков потенциал масштабирования и переиспользования.
2. Без обоснования механика отбрасывается либо вносится как часть существующей системы.

## 4. Введение нового

4.1. Новая функциональность вводится одним из способов, перечисленных ниже в порядке предпочтения. Прежде чем выбрать способ, проверяются совместимость, возможность оптимизации и унификации с имеющимися алгоритмами.

### 4.2. Голова

Требование выражается как дополнение поверх существующей системы: обвязка или параметризация исполнения. Новый узел включает прежнюю систему в себя и не изменяет её. Это основной способ.

### 4.3. Рефакторинг узла

Если головы недостаточно и механизм нужно изменить внутри узла, узел перерабатывается рефакторингом: правки вносятся рекурсивно, последователи приводятся в соответствие. Способ допустим, пока он не затрагивает ожидаемое поведение механизма.

### 4.4. Унифицирующий рефакторинг

Если рефакторинг узла может нежелательно повлиять на ожидаемое поведение, но в узле можно выделить переиспользуемую часть, выполняется унифицирующий рефакторинг:

1. Из прежнего узла выделяется часть, которую он использует сам.
2. Выделенная часть становится предшественником и прежнего узла, и новой механики.
3. Новая механика становится новой головой: включает выделенную часть в себя.

### 4.5. Ромб

Если унифицируемое выделить нельзя, а изменение узла рефакторингом угрожает ожидаемому поведению, применяется ромбирование без потери обратной совместимости:

1. Создаётся близнец узла. У него общие предшественники с прежним узлом.
2. Последователи прежнего узла остаются при нём.
3. Новые последователи, написанные под специализированный механизм, подключаются к близнецу.

4.6. Голова и ромб различаются по назначению: голова добавляет поверх системы, ромб создаёт параллельную ветвь внутри дерева. Ромб применяется тогда, когда голова не закрывает требование поведения полностью.

4.7. Механика, воссозданная с нуля независимо от дерева, ни одним из способов не является и не допускается.

## 5. Приоритеты и разрешение конфликтов

5.1. При конфликте требований действует порядок от высшего приоритета к низшему:

1. Поведение, зафиксированное тестами и ожиданиями автора.
2. Работоспособность и простота реализации: если следование теории утяжеляет реализацию, уступает теория.
3. Положения раздела 3.
4. Удобство и привычки разработчика.

5.2. Отступление от положений при действии пункта 5.1(2) фиксируется с пояснением: какое именно утяжеление возникло бы. Без пояснения отступление недопустимо.

5.3. Теория не служит предлогом для ограничения привычек пользователя и не вводит жёстких защит под чьи-либо привычки: механизм предоставляет возможности, дисциплину обеспечивает автор.

## 6. Процедура допуска и метод аудита

### 6.1. Процедура допуска

Перед написанием кода для любой новой функциональности даются ответы на шесть вопросов. Отрицательный ответ — повод переработать замысел.

1. Нет ли в механизме системы, которая уже решает эту задачу?
2. Какой способ ввода подходит: голова, рефакторинг узла, унифицирующий рефакторинг или ромб (раздел 4)?
3. Если это новая ветвь дерева: чем обоснован фасад и где потенциал переиспользования?
4. Спецификация среды это или управление использованием, и в какой слой оно относится?
5. Разведена ли правка данных и правка алгоритма?
6. Не сирота ли это? Если сирота, её место в файле зерна.

### 6.2. Метод аудита

1. Аудит проводится по фактическому состоянию кода (статическое чтение всего проекта), а не по описанию его устройства.
2. Разделить проект на поведение и реализацию; поведение зафиксировать тестами.
3. Выявить нарушения положений раздела 3: дублирующие реализации, разрозненный доступ к ресурсу, логику ядра в адаптере, неверное направление зависимости, вызовы между параллельными деревьями, мёртвый код, данные в коде, тесты на данные, сирот вне зерна.
4. Для каждого нарушения применить приоритеты раздела 5: утяжеляет ли исправление реализацию? Если да, теория уступает, отступление фиксируется.
5. Распределить находки по шагам рефакторинга. Каждый шаг — отдельное изменение с неизменными поведенческими тестами.
6. После шага проверить тесты.

## Приложение А. Схема слоёв и критерии

```
 Интерфейс среды A            Интерфейс среды B
        │                            │
 Адаптер среды A              Адаптер среды B       (спецификация среды)
        │ вызывает                   │ вызывает
 ┌──────▼────────────────────────────▼──────┐
 │ Интерфейс системы: точки доступа и       │
 │ параметры использования                  │
 ├──────────────────────────────────────────┤
 │ Ядро: дерево единых систем               │
 │ [Система 1]   [Система 2]   [Система 3] │
 └──────▲────────────────────────────▲──────┘
        │ собирает                   │ читает
 Зерно: точка входа и сироты    Данные: тексты и шаблоны
```

Стрелки показывают направление вызова: среда обращается к адаптеру, адаптер — к интерфейсу системы. Параллельные деревья между собой не связаны. Зерно собирает механизм, данные читаются ядром из отдельного хранилища.

| Критерий | Проверка |
|---|---|
| Единственность | Задача решена в одной системе ядра (п. 3.2) |
| Направление зависимостей | Ядро не вызывает и не знает адаптеры (п. 3.4) |
| Управление использованием | Параметр определён в ядре, адаптер лишь переводит запись среды (п. 3.5) |
| Данные | Тексты и шаблоны лежат вне алгоритмов (п. 3.6) |
| Тесты | Проверяют поведение, а не данные (п. 3.7) |
| Неиспользуемый код | Отсутствует (п. 3.8) |
| Сироты | Находятся в файле зерна (п. 3.3) |
