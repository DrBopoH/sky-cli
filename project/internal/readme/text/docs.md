# docs.md — набор документации проекта

Образец для Тебя: какие файлы документации нужны проекту, как они устроены и когда обновляются. Это форма, а не содержание: факты берутся из кода, `.sky/foryou/` и разговора с Автором.

## Правила

1. Начинай с первого именованного коммита. Файл, который нужен проекту, но ещё не написан, считается долгом.
2. Обновляй в том же именованном коммите, где менялось описываемое. Расхождение между файлом и кодом чинится правкой файла после проверки по коду: прав код.
3. Пиши на языке Автора. Зеркала на других языках только по его просьбе.
4. Только факты: что есть и как работает. Без прогнозов, оценок и маркетинга. Планы называй планом.
5. Каждый файл начинается с одной-двух строк: для кого он и по состоянию на какую версию описан.
6. Имена файлов, функций и команд пиши в `коде`. Сравнения и перечни, где у каждого пункта одни и те же поля, оформляй таблицей.
7. Файлы ссылаются друг на друга, а не повторяют друг друга: одно знание живёт в одном месте.

## Состав

| Файл | Для кого | Когда создать | Что внутри |
|---|---|---|---|
| `README.md` (корень) | первый, кто открыл репозиторий | первый коммит | что это и зачем, стек, как собрать и запустить, ссылки на остальное. Пиши по контексту проекта, не по чужому шаблону |
| `CHANGELOG.md` (корень) | пользователь и разработчик | первый именованный коммит | что менялось, по сборкам (структура ниже) |
| `docs/USER.md` | человек, который пользуется продуктом | когда есть что показать | как пользоваться: задачи, а не код |
| `docs/ARCHITECTURE.md` | тот, кто меняет код | первый модуль | устройство: принципы, карта, данные, инварианты |
| `docs/PROJECT-GRAPH.md` | Ты и Автор | первый модуль | реестр модулей и зависимостей (порядок в `readme.md`, раздел «Граф проекта») |
| прочие в `docs/` | по виду проекта | по необходимости | справочник команд, API, форматы данных, операции: имя в верхнем регистре, одна тема на файл |

Файлы в `docs/` называются в верхнем регистре (`ARCHITECTURE.md`). Файлы в `.sky/readme/` строчные и тебе недоступны для записи.

## CHANGELOG.md

Структура:

1. Строка о нумерации: формат версии, где буква состояния, ссылка на регламент.
2. Разделы по сборкам, новые сверху: `## Build N — название (`vR.sB.C+T`), дата`. Пока сборка не вырезана: `## Build N — название (план, `vR.B.C`)`.
3. Внутри раздела по одной строке на именованный коммит: `- **vR.B.C** — что изменилось`. Сверху вниз по убыванию `C`.
4. Раздел «до введения версий» для коммитов без номера: ``- **`хэш`** (ДД.ММ) — что изменилось``. Если номера присваиваются задним числом, скажи об этом в подзаголовке.

Правила записи: одна строка (при необходимости с подпунктами) на одну функцию; пиши, что получил пользователь или проект, а не как это сделано; внутренние коммиты (чистка, тесты, документация) допустимы, если они именованные. Запись добавляется в том же коммите, который её описывает.

Пример записи: `- **v1.2.7** — команда `export`: выгрузка данных в CSV; пустой ввод даёт ошибку вместо пустого файла`.

## USER.md

Структура:

1. Название и один абзац: что делает продукт, что нужно для начала.
2. Содержание со ссылками.
3. «Первый запуск»: минимум шагов до первого результата.
4. «Как данные попадают в продукт» (если применимо): таблица источников.
5. По разделу на страницу, команду или сценарий. Внутри: что видно, что можно сделать, что произойдёт.
6. «Частые вопросы»: короткий вопрос жирным, ответ рядом.

Пиши на «ты», задачами («нажми», «открой»), без внутренних имён функций. Пошаговое и справочное разделяй: шаги нумеруй, справку делай таблицей.

## ARCHITECTURE.md

Структура:

1. Название, для кого файл, по состоянию на какую версию описан, содержание.
2. «Принципы»: нумерованный список, у каждого пункта ключевая фраза жирным и причина.
3. «Карта репозитория»: дерево каталогов, у каждого одна строка комментария.
4. По разделу на подсистему: зачем она, главные типы и функции, как связана с соседними. Границы модулей описывай так же, как в `PROJECT-GRAPH.md`.
5. «Данные»: что где хранится, что можно терять, что нельзя.
6. «Тесты и проверки»: что запускается и что должно быть зелёным.
7. «Инварианты и ловушки»: правила, которые нельзя нарушать, и места, где ошибаются.
8. «Рецепты»: как добавить типовую вещь (новую команду, операцию, источник) по шагам.

Раздел появляется, когда есть что в него положить; пустые заготовки не делай.

## Когда в проекте нет чего-то из набора

Если проект не имеет пользовательской части (библиотека, служебный инструмент), `USER.md` заменяется справочником использования или не создаётся. Если проект не делится на модули, `PROJECT-GRAPH.md` содержит одну запись. Скажи Автору, что пропускаешь и почему.
