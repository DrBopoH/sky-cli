# Регламент оформления исходного текста

MT-code-style · Δρ.ΒοροΗ. · MorangTong creative studio (MTcs) · Редакция 1.0 · 2026-11-25

## Аннотация

Регламент описывает оформление исходного текста: когда нужны комментарии, как записываются выражения и имена, чем и как разделяются части файла. Предмет — правила, по которым код выглядит одинаково независимо от того, кто его пишет. Часть положений восходит к советам Clean Code (комментарий как признак непонятного кода), часть — личные предпочтения автора (запись операций, регистр имён, уровни близости между блоками). Регламент не касается устройства кода и версионирования: для них существуют MT-unify-systems и MT-fix-before-reset.

## 1. Область применения

1.1. Регламент применяется к исходному тексту на любом языке: к коду, к тестам, к сценариям сборки.

1.2. Положения обязательны при написании нового кода, при изменении существующего и при аудите. Устройство систем и версионирование регламентом не регулируются.

1.3. Регламент не зависит от языка программирования. Где язык или обязательный инструмент требует иного (раздел 5), действует требование языка.

1.4. Регламент является инструментом, а не целью. Если следование ему делает код менее понятным, действует раздел 5.

## 2. Термины и определения

| Термин | Определение |
|---|---|
| Отступ | Пустая строка между частями файла. Число отступов выражает близость частей: чем ближе, тем их меньше. |
| Уровень близости | Ступень связи между частями файла (функции, блоки функций, классы, блоки классов, данные), которой соответствует определённое число отступов. |
| Сближенные функции | Функции, решающие смежные задачи и читаемые подряд. |
| Блок | Группа близких друг другу функций, методов или классов. |
| Данные класса | Поля и свойства класса, перечисленные до его методов. |
| Глобальные объявления | Экспортируемые и общие переменные файла. |
| Константы | Неизменяемые значения файла. |
| Шапка | Начало файла: комментарий о файле и список подключаемых модулей. |
| Белый флаг | Комментарий, которым автор признаёт, что не смог написать код понятным. |
| Вода | Комментарии и пояснения в текстах, которые ничего не добавляют к коду или тексту рядом. |

Класс и структура считаются равными понятиями; всё сказанное о классах относится и к структурам.

## 3. Положения

### 3.1. Комментарии

3.1.1. Там, где код говорит сам за себя, комментарий излишен и только занимает место.

3.1.2. Комментарий — белый флаг. Прежде чем его поставить, автор переписывает код так, чтобы пояснение стало не нужно; комментарий остаётся, только если переписать не удалось.

3.1.3. От лишних комментариев и от воды во вложенных пояснениях и текстах избавляются по мере прикосновения к ним: специальных чисток ради них не проводят.

### 3.2. Запись выражений

3.2.1. Присваивание записывается `a = 1`, составное присваивание — `a+= 1`: знак слитно с именем, пробел после него.

3.2.2. Внутри выражения операции `+`, `=` и `-` отделяются пробелами от данных. Операции `*`, `/` и скобки пишутся слитно. Правило распространяется только на выражения: ряд присваиваний (`=`, `+=` и подобные) записывается по 3.2.1.

3.2.3. Пример: `i = (a + b)*(b*c*a**2) + (b - c)`.

### 3.3. Именование

3.3.1. Имена переменных, функций и файлов пишутся в snake_case, как принято в Python.

3.3.2. Если язык навязывает иной регистр (например, регистр первой буквы как признак экспорта), действует правило языка (раздел 5).

### 3.4. Отступы в строке и между частями

3.4.1. Отступ внутри строки выражается табуляцией, а не пробелами.

3.4.2. Части файла разделяются пустыми строками по уровням близости, в порядке от самого близкого к самому дальнему:

| Что разделяется | Пустых строк |
|---|---|
| Сближенные функции внутри блока | 1 |
| Блоки сближенных функций между собой | 2 |
| Данные класса и его методы | 2 |
| Блоки близких методов между собой (внутри блока методы разделяются одной) | 2 |
| Близкие классы между собой | 3 |
| Блоки близких классов между собой | 4 |
| Классовый или функциональный блок кода и глобальные объявления | 4 |
| Глобальные объявления и константы | 2 |
| Длинный список подключаемых модулей в шапке и остальной код (редко) | 5 |

3.4.3. Число пустых строк не заменяется комментариями-разделителями: границу между частями показывает сам файл.

### 3.5. Шапка файла

3.5.1. Комментарий в шапке с относительным путём файла в проекте допускается, но не требуется: это наследие времён агентов без хорошего контекста и памяти. В новом коде его не ставят, существующий не вычищают отдельной работой.

## 4. Обоснование

4.1. Положения 3.1 восходят к совету Clean Code: комментарий — не украшение, а признание в том, что код не выразил замысел. Остальные положения — личный выбор автора: единая запись операций, snake_case и табуляция упрощают чтение подряд идущих выражений и имён.

4.2. Уровни близости (3.4.2) заменяют пустые строки «на вкус» измеримой шкалой: по числу отступов видно, насколько связаны части файла, не читая их.

## 5. Приоритеты и разрешение конфликтов

5.1. При конфликте требований действует порядок от высшего приоритета к низшему:

1. Требования языка и обязательных инструментов форматирования (например, `gofmt`, регистр экспорта в Go).
2. Понятность кода: если следование регламенту делает его менее понятным, уступает регламент.
3. Положения раздела 3.
4. Привычки разработчика.

5.2. Отступление по пункту 5.1(1) или 5.1(2) фиксируется с пояснением: что именно навязал язык или в чём пострадала бы понятность. Без пояснения отступление недопустимо.

5.3. Регламент не служит предлогом для жёстких защит от привычек разработчика: он описывает оформление, дисциплину обеспечивает сам автор.

## 6. Процедура допуска и метод аудита

### 6.1. Процедура допуска

Перед внесением кода автор проверяет:

1. Каждый комментарий: нельзя ли переписать код так, чтобы он не понадобился (3.1.2).
2. Запись операций и присваиваний (3.2).
3. Регистр имён, с оговоркой языка (3.3).
4. Табуляцию для отступа внутри строки (3.4.1).
5. Число пустых строк между частями по таблице 3.4.2.

### 6.2. Метод аудита

Аудит идёт по тем же пяти пунктам, по файлу сверху вниз. Результат записывается по критериям приложения А; отступления без пояснения по 5.2 считаются нарушениями.

## Приложение А. Схема уровней и критерии

Уровни от ближнего к дальнему (число — пустые строки между частями):

```
функция          1  функция                      (внутри блока функций)
блок функций     2  блок функций
данные класса    2  методы                       (внутри класса)
блок методов     2  блок методов
класс            3  класс                        (близкие классы)
блок классов     4  блок классов
блок кода        4  глобальные объявления
глобальные       2  константы
шапка            5  остальной код                (редко)
```

Пример записи (отступ в строке — табуляция):

```
sub(a, b):
	return a - b

mult(a, b):
	return a*b
```

| Критерий | Проверка |
|---|---|
| Комментарии | Каждый нужен и не заменим кодом (п. 3.1) |
| Выражения | Запись операций и присваиваний по п. 3.2 |
| Имена | snake_case с оговоркой языка (п. 3.3) |
| Табуляция | Отступ в строке выражен табуляцией (п. 3.4.1) |
| Пустые строки | Число соответствует уровню близости (п. 3.4.2) |
| Шапка | Путь файла не обязателен (п. 3.5) |
