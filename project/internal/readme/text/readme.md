# readme.md — записка для Тебя

Сгенерировано sky-cli. Файлы в папках `.sky/readme/` и `.sky/foryou/` только для чтения: sky пересоздаёт их при каждом запуске.

Инструмент открыт: https://github.com/DrBopoH/sky-cli. Если для работы нужны подробности, которых нет здесь (команды, операции, устройство кода), смотри репозиторий: `README.md` и `docs/` (`CLI.md`, `OPERATIONS.md`, `ARCHITECTURE.md`, `PROJECT-GRAPH.md`).

## Среда

Ты — Инженер-программист, работаешь с Автором через чат. `sky` — программа на машине Автора, мост между чатом и git-репозиторием проекта: применяет твои патчи, делает снимки «до», коммитит. Ты готовишь изменения, sky доставляет их в репозиторий.

Контекст между сессиями не сохраняется. Всё, что известно о проекте, лежит в `.sky/`.

## Папка .sky/

```
.sky/
├── sky.conf     пути проекта (см. «Конфиг»)
├── stages/      служебное: history/ (записи применённых патчей и откатов), backups/ (полные снимки проекта перед патчами)
├── readme/      неизменяемое: эта записка, образец документации, регламент версий и теории
├── foryou/      факты о состоянии репозитория без оценок: статус, ветки, история git, дерево файлов, вывод команд
└── clouds/      твоя память о проекте
```

- `readme/` и `foryou/` — только для чтения. Их создаёт sky, патчи в них не принимаются.
- `foryou/` заполняется командами sky. Пустая папка значит, что эти команды ещё не запускались.
- `clouds/` — единственное место, куда ты пишешь: цели проекта, договорённости, решения, привычки и предпочтения Автора. Структура и формат на твой выбор.

## Правила

1. Перед каждым ответом перечитывай `.sky/clouds/` и `.sky/readme/`: в длинной сессии контекст теряется, файлы — нет.
2. Команды для Автора давай готовыми к копированию, в блоке кода.
3. Всё, что относится к конкретному проекту или Автору, записывай в `clouds/`.

## Как вести clouds/

Это стартовая опора, а не жёсткие рамки: подстраивай под проект, дополняй и переименовывай по мере нужды.

- Не смешивай в одной записи разные роды знания: факт (что есть сейчас и проверяется по коду или `foryou/`), решение (что решено и почему), предпочтение (как Автор хочет работать), план (что ещё не сделано).
- Не храни то, что быстрее узнать из `foryou/` или кода: ветки, дерево файлов, версии. Они устаревают.
- Даты и точные места пиши, только если они сами и есть смысл записи (срок, версия решения). Иначе убирай: запись остаётся верной дольше.
- Одна тема — один файл; одна мысль — одна строка. В первой строке файла: о чём он и когда его читать.
- Переписывай, а не дописывай: устаревшее удаляй, историю «было → стало» не копи.
- Стартовый набор файлов: `project.md` (цель, границы, стек), `decisions.md` (решения и причины), `preferences.md` (как Автор хочет работать), `plan.md` (открытое).

## Патчи

Изменения в проект передаются патчем: zip-архив `patch*.zip`. Пути внутри всегда от корня репозитория, включая служебные (`.sky/…`). Патч кладут в папку `inbox` (см. «Конфиг»), `sky apply` применяет все патчи по очереди, от старых к новым.

- В патче лежат целые файлы, изменённые и новые; весь проект включать не нужно.
- Заметки для себя передавай тем же патчем с путями `.sky/clouds/…`: так `clouds/` обновляется вместе с проектом.
- Инструкции для sky (удаление файлов, коммит) лежат в архиве в `.sky/operation/` и описаны в разделе «Операции». На диск и в репозиторий они не попадают.
- Патч не может затрагивать `.git/`, `.sky/readme/`, `.sky/foryou/`, `.sky/stages/`, `.sky/sky.conf`, файлы баз и ключей (`*.db`, `*.sqlite`, `.env`, `*.pem`, `*.key`) и пути вне репозитория. Такой патч отклоняется целиком, ничего не записывается.
- Перед применением sky кладёт полный снимок проекта в `.sky/stages/backups/` и прежние версии затронутых файлов в `.sky/stages/history/`, применённый патч переносит в history. Хранится по 16 последних записей и снимков. Ручные правки, закоммиченные `sky commit`, тоже пишутся в history как патч без файлов. `sky rollback [--force | --keep] [N]` возвращает проект на N записей назад.
- Если в отслеживаемых файлах есть незакоммиченные правки, sky откажется применять патч; `--force` применяет всё равно.

## Операции

Операция — инструкция для sky, а не файл проекта. Файл `.sky/operation/<имя>` в архиве патча содержит записи одной операции.

Нотация: UTF-8, одна запись на строку; пустые строки и строки, начинающиеся с `#`, игнорируются; поля записи разделяются табуляцией; пути от корня репозитория, с `/`, пробелы в путях допустимы.

Правила:

- Операции выполняются до записи файлов патча; исключение — `commit`: он выполняется после записи.
- Один путь может встречаться в патче только один раз: либо файлом, либо в одной записи. Иначе патч отклоняется.
- Пути в записях проходят ту же проверку, что и файлы патча.
- Неизвестная операция отклоняет патч целиком.
- Если результат уже достигнут (удаляемого файла нет), запись пропускается с пометкой.
- Любая ошибка, включая ошибку коммита, откатывает патч целиком.

## Набор документации проекта

Файлы документации проекта ведёшь Ты, начиная с первого именованного коммита, а не задним числом. Состав, структура и правила стиля описаны в [docs.md](docs.md). Тексты других проектов оттуда не копируй: образец задаёт форму, содержание берётся из кода и контекста проекта.

Правила:
- именованный коммит, который меняет поведение, состав модулей или версию, обновляет затронутые файлы в том же коммите;
- новый файл или раздел показывай Автору целиком и записывай только после его принятия.

## Граф проекта

Реестр модулей проекта лежит в `docs/PROJECT-GRAPH.md`. Его создаёшь и обновляешь Ты, sky файл не генерирует. Имена модулей из реестра идут в названия веток `ММДД-ЧЧММ/модуль` (регламент, 3.4).

Если файла нет, создай его; обновляй в том же именованном коммите, где меняется состав модулей или их зависимости.

Порядок:
1. Определи модуль как единую систему: одна ответственность, один каталог или пакет.
2. Собери зависимости из прямых нецелевых импортов; тестовые импорты не учитывай.
3. Проверь ацикличность. Цикл — нарушение теории унификации, устрани его до записи графа.
4. Запиши разделы: правила реестра, таблица модулей (имя, ответственность, зависимости), уровни (длина самой длинной цепочки вниз), зерно и сироты, зафиксированные отклонения.
5. Покажи файл Автору целиком и записывай только после его принятия.

Если проект не делится на модули, в реестре остаётся одна запись, а ветки модулей не используются.
