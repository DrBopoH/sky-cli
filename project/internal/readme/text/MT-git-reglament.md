# Регламент практического применения теории обратного инкремента в системах слежения версий

MT-git-reglament · Δρ.ΒοροΗ. · MorangTong creative studio (MTcs) · Редакция 2.0 · 2026-11-25

## Аннотация

Регламент описывает, как нумерация по теории обратного инкремента реализуется в системе контроля версий git. Предмет — две области работы (локальная и удалённая), граф удалённых веток, построенный по графу систем проекта, именованные коммиты, сборки и их исправления, публикация. Результат — правила, при которых каждая версия указывает на точный коммит, история остаётся читаемой, а структура веток повторяет структуру зависимостей проекта. Регламент опирается на две теории: [MT-fix-before-reset](MT-fix-before-reset.md) (смысл и рост частей версии) и [MT-unify-systems](MT-unify-systems.md) (системы, зависимости, зерно).

## 1. Область применения

1.1. Регламент применяется к проектам, которые ведутся в git и версионируются по схеме `vR.sB.C+T.hash`.

1.2. Регламент определяет устройство веток, момент присвоения версии, формат сообщений и порядок слияний. Смысл и рост частей версии регулирует теория обратного инкремента.

1.3. Определения состояний `a`, `b`, `s` принадлежат регламенту (п. 3.6.7). Состояние `m` определяет теория.

1.4. Регламент является инструментом, а не целью. При конфликте с требованиями поведения и скорости действует раздел 5.

## 2. Термины и определения

| Термин | Определение |
|---|---|
| Модуль | Система проекта как узел графа зависимостей. «Модуль» — имя термина, а не записываемое имя ветки. |
| Граф проекта | Файл-описание (по умолчанию `docs/PROJECT-GRAPH.md`), описывающий модули проекта и направления зависимостей по теории унификации. Служит реестром модулей. |
| Зерно | Точка входа проекта. Роль зерна играет ветка `dev`. |
| Локальная ветка | Ветка автора с атомарными коммитами, названная по вводимой фиче. Существует только на машине автора. |
| Атомарный коммит | Минимальное завершённое изменение внутри локальной ветки. |
| Именованный коммит | Коммит удалённого графа, в который сжата локальная ветка фичи. Несёт резюме и версию. |
| Ветка модуля | Удалённая ветка `модуль/ММДД-ЧЧММ`, в которой живёт секция изменений одного модуля. |
| Сборка | Для нативных приложений — компиляция; для веб-приложений — выкладка версии, например на тестовый сервер. |
| Ветка сборки | Удалённая ветка `build/ММДД-ЧЧММ`, фиксирующая сборку и её исправления. |
| Исправление сборки | Следующая сборка в ветке сборки с правкой после найденной проблемы; версия `R.sB-F.C`. |
| Кристаллизация | Перенос исправления из ветки сборки в `dev` ветками модулей по уровням и по теориям. |

## 3. Положения

### 3.1. Области работы

1. Работа делится на две области: локальную и удалённую. Правила областей независимы.
2. **Локальная область.** Ветка называется по вводимой фиче. В ней разрешён шум: удаление, возврат, переписывание. Атомарные коммиты записываются по Conventional Commits: `feat|fix|refactor|perf|test|docs|style|chore: текст`, после типа до 72 символов. Ветка остаётся у автора.
3. **Удалённая область.** Запрещены авторский push, force-push и push локального слияния. Всё идёт через pull request, автоматические проверки и ревью. Удаление веток `main`, `dev` и веток сборки запрещено.
4. Локальная ветка попадает в удалённую область через pull request из `wip`-ветки. Этот путь обходит запрет push и лежит в основе всей схемы личных веток с атомарными коммитами.
5. Удалённая область принимает локальную ветку как один именованный коммит (squash).

### 3.2. Граф удалённых веток

```
main                  ◄── сборки (squash, только из ветки сборки)
dev                   ◄── слияния веток модулей (зерно)
модуль/ММДД-ЧЧММ      ветки модулей, вложенные по цепочке зависимостей
build/ММДД-ЧЧММ       ветка сборки: от последнего коммита dev
```

1. Слияния происходят только между удалёнными ветками.
2. Слияние между ветками модулей и в `dev` — merge-коммит: именованные коммиты внутри остаются видны.
3. Слияние в `main` — squash и только из ветки сборки (п. 3.7).
4. Стартовый коммит `main` фиксирует момент создания проекта. От него отходит `dev`.

### 3.3. Зерно

1. `dev` — зерно: изменения точки входа не требуют ветки модуля.
2. Каждое изменение зерна — именованный коммит прямо в `dev` (через pull request из `wip`-ветки). Он получает полную версию.

### 3.4. Модули и цепочки

1. Ветка модуля называется `модуль/ММДД-ЧЧММ`, например `storage/1125-1020`. Год в имени не нужен. Модуль идёт первым сегментом: git группирует ветки по первому слову как папки, и ветки одного модуля лежат рядом, а не вперемешку по датам.
2. Имя модуля берётся из графа проекта. Нового имени без правки графа не бывает: реестр модулей — граф проекта, а не набор веток.
3. Глобальных веток на модуль нет (одна `api` на все изменения). Дата замыкает цикл изменений на конкретной секции: общая ветка повторила бы вид `dev`, принесла бы большие слияния и конфликты.
4. Перед работой определяется цепочка модулей, которую правка затрагивает по графу проекта: например, `dev → api → domain → storage`.
5. Ветки вкладываются по цепочке: `api` от `dev`, `domain` от `api`, `storage` от `domain`.
6. Секции расходятся параллельно, если правят разные узлы: один правит `storage`, другой `cache`.
7. Слияние идёт снизу вверх. Каждый уровень подстраивается под изменение ниже и сливается выше; в `dev` попадает слияние верхней ветки.
8. Рефакторинг распределяет именованные коммиты по веткам и уровням зависимостей, а не выстраивает их линейно.
9. Граф проекта является источником: структура не пересобирается мысленно. Изменение, меняющее граф (новый модуль, перенос зависимости), обновляет файл графа в том же изменении.

### 3.5. Именованные коммиты и версия

1. Каждый именованный коммит, включая слияние, прибавляет `C`.
2. В `dev` именованный коммит пишет полную версию `vR.B.C+T.hash`.
3. Именованные коммиты внутри веток модулей пишут только счётчик и хэш: `vC.hash`. `R` и `B` на ветках модулей не пишутся: их определяет `dev` в момент слияния.
4. Слияние ветки модуля в `dev` — именованный коммит с полной версией. Пример: коммит на ветке `v28.abc1234`, слияние в `dev` — `v1.1.29+29.abc1234` (хэш вершины вливаемой ветки).
5. На ветке модуля `C` провизорный: значение `C` в `dev` в момент ответвления плюс порядковый номер именованного коммита в ветке.
6. Слияние в `dev` получает `C` = `C` в `dev` + число именованных коммитов ветки + 1. Параллельные ветки показывают одинаковые номера на момент ответвления (`v28` и `v28`); окончательные номера назначает `dev` по порядку слияний. Пример: `C` в `dev` равно 27, первая ветка с одним коммитом даёт слияние 29 (коммит ветки занимает 28), вторая ветка с одним коммитом — слияние 31 (её коммит занимает 30). Номер всегда восстанавливается подсчётом именованных коммитов в истории `dev`.
7. Сообщение именованного коммита:
   - на ветке модуля: `Краткое резюме фичи | v28.abc1234`;
   - в `dev`: `Краткое резюме фичи | v1.1.29+29.def5678`.
8. Резюме пишется по-английски. Хэш — короткий (7 символов) идентификатор вершины источника: последнего коммита ветки фичи при squash, вершины вливаемой ветки при merge. Собственный хэш коммит в своём сообщении записать не может.
9. `T` — число всех именованных коммитов и исправлений сборок (`C` + `F`) текущего `R`. Оно растёт с каждым именованным коммитом `dev` и с каждым исправлением и сбрасывается только после роста `R`. Пример: сборка `1.a1.31+31` с двумя исправлениями (`1.a1-1.31+32`, `1.a1-2.31+33`); первое изменение следующей сборки — `1.2.1+34`.

### 3.6. Сборки

1. Сборка фиксируется на последнем коммите `dev`: от него отходит ветка сборки. Это выход версии, а не именованное изменение.
2. Хвост ветки сборки — коммит с буквой состояния: `v1.a1.29+29.abc1234`. Он копирует голову `dev`: то же дерево, родитель — вершина `dev`; меняются только сообщение (название сборки) и буква в версии. Хэш в сообщении — вершина `dev`, с которой снята сборка.
3. Следующие сборки с исправлениями увеличивают `F`: `v1.a1-1.29+30.def5678`, `v1.a1-2.29+31.9a8b7c6` и далее. Голова ветки — последнее исправление (девять исправлений дают `v1.a1-9.29+…`).
4. При исправлении `C` не растёт, `T` растёт (теория, п. 3.5).
5. Удалённой ветки для исправлений нет: ветка сборки — единственное место исправлений. Локальная ветка исправления отводится от ветки сборки и ложится в неё одним squash-коммитом. Её исправляющая часть — фича с атомарными коммитами с префиксом `-F` и особой записью версии, выделенной для удалённого графа.
6. Исправление может нарушать положения теорий и регламента, если нужны поведение и скорость.
7. Состояния:
   - `a` (alpha) — прототип, черновая структура, сырой исходный код;
   - `b` (beta) — идёт проверка, базовая структура определена, системы интегрированы;
   - `s` (stable) — версия пригодна для промежуточного или ночного использования;
   - `m` определяется теорией.
8. Состояние присваивается решением команды.
9. Нативное приложение: сборка — компиляция. Веб-приложение: сборка — выкладка версии, например на тестовый сервер.
10. Первое именованное изменение после выхода сборки — `B` +1, `C` = 1 (теория, п. 3.1).

### 3.7. Кристаллизация и публикация

1. Вливать ветку сборки в `dev` запрещено.
2. Изменения из ветки сборки вносятся в `dev` последовательно, размеренно, по уровням и по теориям: чисто, но не стерильно. Для этого заводятся обычные ветки модулей; результат — именованные коммиты в `dev`.
3. `main` — ветка смысла «релиз»: в неё попадают отобранные качественные сборки (нативные) или проверенные выкладки (веб), чтобы опубликовать их как общедоступные.
4. В `main` вливается только ветка сборки, одним squash-коммитом. Одна опубликованная сборка — один коммит в `main`, его версия — версия головы ветки сборки.
5. Слияние в `main` не меняет `R`: рост `R` — решение команды (теория, п. 3.3).

### 3.8. Гранулярность

1. Именованные коммиты частые: один на законченную возможность, под ним 2–6 атомарных.
2. Фуллстек-фича режется на атомарные по слоям и смыслу, а не одним коммитом на всё.
3. Правка к фиче до слияния — ещё один атомарный коммит в той же локальной ветке.
4. Правка к фиче, уже влитой в `dev`, — отдельная ветка модуля и отдельный именованный коммит.

## 4. Сценарии

1. **Правка модуля.** Локальная ветка → именованный коммит на ветке модуля → слияние вверх по цепочке → `dev` (полная версия).
2. **Правка зерна.** Локальная ветка → pull request → именованный коммит в `dev`.
3. **Параллельная секция.** Две ветки правят `storage` и `cache`, обе сливаются в `domain`; `domain` подстраивается; затем `api`; затем `dev`.
4. **Сборка.** Ветка сборки от последнего коммита `dev`: `1.a1.29`. Найдена проблема: `1.a1-1.29`.
5. **Кристаллизация.** Ветки модулей по уровням, затем `dev`.
6. **Публикация.** Выбранная сборка вливается в `main` одним squash-коммитом.
7. **Без удалённого репозитория.** Pull request заменяется локальным слиянием; правила графа и версий те же.

## 5. Приоритеты и разрешение конфликтов

5.1. При конфликте требований действует порядок от высшего приоритета к низшему:

1. Поведение и скорость исправления.
2. Достоверность версии: номер однозначно указывает на коммит.
3. Положения раздела 3.
4. Удобство и привычки автора.

5.2. Исправление сборки может нарушать положения (п. 3.6.6). Кристаллизация возвращает правила в `dev`.

5.3. Отступление от положений фиксируется с пояснением: что именно усложнило бы выполнение правила. Без пояснения отступление недопустимо.

## 6. Процедура допуска и метод аудита

### 6.1. Процедура допуска

Перед слиянием или публикацией даются ответы на шесть вопросов. Отрицательный ответ — повод пересмотреть действие.

1. Названа ли ветка по правилам области (фича локально, `модуль/ММДД-ЧЧММ` удалённо), и есть ли модуль в графе проекта?
2. Определена ли цепочка модулей по графу, и идут ли слияния снизу вверх?
3. Правильный ли тип слияния: merge между удалёнными ветками, squash из локальной ветки и в `main`?
4. Верно ли записана версия: полная в `dev`, `vC.hash` на ветках модулей?
5. Если выходит сборка: присвоено ли состояние решением команды, не влита ли ветка сборки в `dev`?
6. Обновлён ли граф проекта, если изменение меняет структуру?

### 6.2. Метод аудита

1. Аудит проводится по фактическому графу веток и истории версий, а не по описанию.
2. Выявляются нарушения положений раздела 3: глобальные ветки на модуль, слияния не по цепочке, неверный тип слияния, версии не по формату, слияние ветки сборки в `dev`, граф проекта не соответствует модулям.
3. Для каждого нарушения применяются приоритеты раздела 5.
4. Находки распределяются по шагам исправления; каждый шаг — отдельное изменение.

## Приложение А. Схема и критерии

```
 локальная ветка фичи ──squash──► ветка модуля (именованный коммит, vC.hash)
 ветка модуля ──merge──► вышележащая ветка модуля ──merge──► dev (vR.B.C+T.hash)
 dev ──последний коммит──► ветка сборки (v1.a1.C, затем v1.a1-F.C)
 ветка сборки ──squash──► main (один коммит на сборку)
 ветка сборки ──кристаллизация, не слияние──► dev
```

| Критерий | Проверка |
|---|---|
| Именование веток | Фича локально; `модуль/ММДД-ЧЧММ` удалённо; модуль есть в графе |
| Цепочка | Слияния снизу вверх по зависимостям |
| Тип слияния | Merge между удалёнными ветками; squash из локальной и в `main` |
| Версия | Полная в `dev`, `vC.hash` на ветках модулей, `R.sB-F.C+T.hash` в сборках |
| Сборка | Ветка сборки не вливается в `dev` |
| `main` | Только squash из ветки сборки, `R` не растёт автоматически |
| Граф проекта | Соответствует модулям и зависимостям |
