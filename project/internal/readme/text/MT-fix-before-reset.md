# Теория версионирования обратным инкрементом

MT-fix-before-reset · Δρ.ΒοροΗ. · MorangTong creative studio (MTcs) · Редакция 1.0 · 2026-11-25

## Аннотация

Теория описывает способ нумерации версий, в котором значение разряда фиксируется до его сброса, а не после. Предмет — смысл частей номера `vR.sB.C+T.hash`, правила их роста и состояния сборки. Результат — номер, который называет только существующее: версий с нулём, обозначающим пустой разряд, не бывает. Теория не зависит от системы контроля версий и способа публикации; ветки, слияния и автоматизация относятся к регламенту, построенному на ней.

## 1. Область применения

1.1. Теория применяется к нумерации версий продуктов, в которых готовые возможности накапливаются последовательно и группируются в сборки.

1.2. Положения обязательны при присвоении версии и при аудите истории версий. Способ получения номера (вручную, скриптом, CI) и устройство веток теорией не регулируются: для них существует отдельный регламент.

1.3. Теория не зависит от языка программирования, системы контроля версий и формы поставки продукта.

1.4. Теория является инструментом, а не целью. Если следование ей мешает работе с внешней экосистемой, действует раздел 5.

## 2. Термины и определения

| Термин | Определение |
|---|---|
| Именованное изменение | Одна законченная возможность, которую можно назвать одной строкой журнала изменений. Обычно воплощается одним коммитом. |
| Заморозка | Событие, в котором именованное изменение получает версию. |
| Сборка | Набор возможностей одного контекста (тема), выпускаемый как целое. |
| Состояние | Степень зрелости сборки: `a`, `b`, `s`, `m`. |
| Цикл продукта | Последовательность «вход → обработка → отдача»: продукт принимает данные или действия из среды, преобразует их по собственным правилам и возвращает результат, который воспринимает получатель и который приносит ему пользу. |
| Сброс разряда | Возврат младшего разряда к начальному значению после роста старшего. |
| Прямой инкремент | Принятый в SemVer порядок: разряд растёт, младшие обнуляются, номер с нулём считается версией: `1.1.29` → `1.2.0`. |
| Обратный инкремент | Порядок, в котором значение разряда фиксируется до сброса, а нулевое значение не становится версией: `1.1.29` → `1.2.1`. |

## 3. Положения

### 3.1. Обратная фиксация

1. Значение разряда записывается в момент события, которое его создало, до сброса младших разрядов.
2. Сброс происходит после фиксации и вступает в силу со следующим именованным изменением: оно записывается со значением `1`.
3. Первое именованное изменение сборки несёт `C` = 1. Первое именованное изменение новой сборки несёт `B` +1 и `C` = 1 одновременно: следующая сборка после `1.1.29` начинается с `1.2.1`.
4. Версия `X.Y.0` не создаётся: она обозначала бы пустую сборку, которой не существует. Хвостовых `.0` в номере нет.
5. Первой версией считается `1.1.1`: открыта разработка первого поколения (`R` = 1), первой сборки (`B` = 1), зафиксировано первое изменение (`C` = 1).

### 3.2. Части версии

Форма записи: `vR.sB.C+T.hash`.

| Часть | Что означает | Как меняется |
|---|---|---|
| `R` | Release, поколение продукта. Оповещает о ломающих изменениях | Только решением человека |
| `s` | Состояние сборки | Решением команды, `a` → `b` → `s` → `m` |
| `B` | Build, номер сборки | +1 при выходе сборки |
| `C` | Commit, вес сборки | +1 за каждое именованное изменение внутри сборки |
| `T` | Total, число всех именованных изменений и исправлений текущего `R` | +1 за каждое именованное изменение и каждое исправление, между сборками не сбрасывается |
| `hash` | Короткий хэш (7 символов) замораживаемого изменения | Определяется заморозкой |

Пользователю достаточно `R.sB`, иногда `R.sB.C`. Часть `+T.hash` нужна разработчику и точно указывает источник версии.

### 3.3. Рост разрядов

1. `C` и `T` растут на единицу с каждым именованным изменением. `C` относится к сборке, `T` — к поколению `R`; `T` растёт также с каждым исправлением сборки.
2. `C` растёт до фиксации сборки. Выход сборки увеличивает `B`; `C` начинается заново со следующего именованного изменения (п. 3.1).
3. `R` растёт только решением человека. Слияние в основную ветку или публикация `R` не повышают: смысл разряда — оповестить об изменениях, ломающих совместимость.
4. После роста `R` разряды `B`, `C` и `T` начинаются заново: следующее именованное изменение записывается как `R.1.1+1`.

### 3.4. Состояние

1. Состояние обозначает зрелость сборки, а не её размер и срок. Порядок: `a` → `b` → `s` → `m`; рост идёт слева направо: массивнее, стабильнее, полезнее. Состояние `a` самое частое.
2. Точные определения `a`, `b` и `s` задаёт регламент проекта, в теорию они не входят. Состояние `m` определяется теорией: версия, замыкающая цикл продукта (раздел 2), завершённая и задокументированная.
3. Продукт, не замыкающий цикл, неполноценен и состояния `m` не получает. Содержание этапов определяет тип продукта: для утилиты это сбор данных из системы, обработка по модификаторам и фильтрам и вывод в читаемом виде; для игры — приём действий игрока, расчёт состояния мира и отклик, на который игрок отвечает следующим действием.
4. Букву состояния получает не отдельное изменение, а сборка в момент фиксации. До фиксации версии изменений записываются без буквы: `v1.1.29+29.abc1234`.
5. Фиксация происходит компиляцией: последнее именованное изменение сборки переносится в поток сборок и получает букву, номер сохраняется: `1.1.29` → `1.a1.29`. Следующее именованное изменение входит уже во вторую сборку и записывается `1.2.1`.
6. Состояние присваивается решением команды.

### 3.5. Исправления выпущенной сборки

1. Исправление сборки, уже получившей состояние, не открывает новую сборку.
2. Версия исправления: `vR.sB-F.C+T.hash`, где `F` — порядковый номер исправления этой сборки.
3. При исправлении растут `F` и `T`; `C` остаётся прежним. Исправления сборки `1.a1`, закрытой на `C` = 29, записываются `1.a1-1.29`, `1.a1-2.29`, `1.a1-3.29`.

### 3.6. Хэш

1. Хэш в версии — короткий (7 символов) идентификатор замораживаемого изменения.
2. Он связывает номер с конкретным состоянием проекта: по версии можно найти точный источник.

## 4. Обоснование и сопоставление

4.1. Хвостовой ноль в прямом инкременте — следствие фиксации после сброса: при росте старшего разряда младшие обнуляются, и в номер попадает состояние пустого разряда. Поэтому до пользователя большинство продуктов доходит с `.0` на конце.

4.2. Нулевое значение исторически несёт смысл «не завершено»: версии `0.x` обозначают сырой продукт. Счёт с нуля делает первой версией `0.0.0`, не имеющую содержания.

4.3. Схема `X.Y.Z` создавалась в эпоху конфликтов зависимостей, чтобы выразить степень нарушения совместимости: ломающее изменение, новая возможность, малое исправление. Со временем номер получил маркетинговую нагрузку и отошёл от технического смысла.

4.4. Схема `vR.sB.C+T.hash` сложнее, но до пользователя доходит обычно только `R.sB` или `R.sB.C`; остальное нужно разработчику.

4.5. Сопоставление форм записи (значения для обратного инкремента взяты для примера):

| Схема | Пример |
|---|---|
| SemVer | `0.16.0` |
| Zig | `0.16.0-dev.2632+84f84267c` |
| Обратный инкремент | `16.b232.67+2632.84f84267c` |

4.6. Сопоставление поведения:

| Событие | Прямой инкремент | Обратный инкремент |
|---|---|---|
| Первая версия | `0.1.0` или `1.0.0` | `1.1.1` |
| Конец сборки → начало следующей | `1.1.29` → `1.2.0` | `1.1.29` → `1.2.1` |
| Версия без изменений внутри | существует | не существует |
| Смысл нуля в разряде | «пока ничего» | не используется |

## 5. Приоритеты и разрешение конфликтов

5.1. При конфликте требований действует порядок от высшего приоритета к низшему:

1. Достоверность: номер называет только существующее и однозначно указывает на источник.
2. Совместимость с внешней экосистемой: если инструмент (менеджер пакетов, магазин приложений) требует `X.Y.Z`, уступает теория.
3. Положения раздела 3.
4. Удобство и привычки автора.

5.2. Отступление от положений при действии п. 5.1(2) фиксируется с пояснением: какое требование экосистемы его вызвало и как внутренняя версия отображается во внешнюю. Без пояснения отступление недопустимо.

5.3. Теория не регулирует, какое событие считать именованным изменением: это определяет регламент проекта.

## 6. Процедура допуска и метод аудита

### 6.1. Процедура допуска

Перед присвоением версии даются ответы на шесть вопросов. Отрицательный ответ — повод пересмотреть номер.

1. Существует ли именованное изменение, которое получает версию?
2. Какие разряды растут и какие остаются прежними?
3. Растёт ли разряд только после появления того, что он считает (нет версий с нулём)?
4. Если выходит сборка, присвоено ли состояние решением команды (для `m` — замкнут ли цикл)?
5. Требует ли событие роста `R`, и принято ли такое решение человеком?
6. Не потребует ли внешняя экосистема отступления, и зафиксировано ли оно?

### 6.2. Метод аудита

1. Аудит проводится по фактической истории версий, а не по описанию схемы.
2. Выявляются нарушения положений раздела 3: версии с нулём, сброс без события, уменьшение `T`, буква состояния у версии отдельного изменения, рост `R` без решения.
3. Для каждого нарушения применяются приоритеты раздела 5.
4. Находки распределяются по шагам исправления; каждый шаг — отдельное изменение.

## Приложение А. Схема счётчиков и критерии

```
 именованное изменение  ─►  C +1, T +1  (до фиксации сборки)
 фиксация сборки        ─►  буква состояния, номер сохраняется (1.1.29 → 1.a1.29)
 следующее изменение    ─►  B +1, C = 1  (1.2.1)
 исправление сборки     ─►  F +1, T +1, C не меняется (1.a1-1.29)
 решение о ломающих     ─►  R +1; B, C, T начнутся заново со следующего изменения
 изменениях
```

| Критерий | Проверка |
|---|---|
| Нет пустых версий | В номере нет `.0` как значения разряда |
| Фиксация перед сбросом | Сброс не создаёт отдельной версии |
| `T` не сбрасывается | Растёт монотонно в пределах `R` |
| `R` не автоматичен | Меняется только решением человека |
| Состояние на сборке | Буква стоит у зафиксированной сборки, номер сохраняется; версии изменений до фиксации без буквы |
| Цикл для `m` | Продукт принимает, обрабатывает и отдаёт результат |
